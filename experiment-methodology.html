How the loading experiments are measured

Three strategies ask different questions

The first experiment runs three passes for the same image. A progressively requests each new resolution until the target is reached. B fetches that target's complete prefix and decodes once. C fetches every resolution the master allows and decodes once.

A and B transfer the same image-body information for the same target. A adds requests and decodes to show an earlier frame; B avoids those intermediate steps. C measures the cost of loading the original when the display needs fewer pixels. The current-level readout stays attached to the decoded frame, including after a pass finishes.

The passes run sequentially. “Run all speeds” repeats these passes under each bandwidth profile, producing twelve rows. The codec is initialized before timing begins. Fresh run URLs and Cache-Control: no-store prevent the experiments from relying on a previous image response.

Limit real download speed

A local proxy limits the rate at which actual image bytes reach the browser. It also adds a small delay to each request. The demos use real decoding rather than an animation that pretends to load.

Demo sits between Everyday and Fast to keep a run short enough to watch while leaving room to see the loading stages. These profiles shape downloads locally; they do not recreate every behavior of a mobile or home connection.

Load concurrently without multiplying bandwidth

The gallery experiment starts ten different images in each row. Both rows receive the same total download rate, shared across their ten images. Concurrent loading does not give each image a separate full-speed connection.

Both rows send delay and rate settings in request headers. The PNG row fetches each complete original and displays it through an object URL; its timing includes full-body download and image decoding. Python listens on four transfer ports, 3434–3437, with two origins for each row. Port 3434 also handles configuration and cancellation. Each row shares one speed limit; browser and CDN connection scheduling still apply. Requests without shaping headers have no added latency or bandwidth limit.

Experiments run one at a time. Stop cancels the current run so settings can be changed. A frame already being decoded may finish before the browser handles the stop.

How long should the PNG row take?

The ten original PNGs total about 6.24 MB. Their expected download time depends on the shared rate:

Emage needs about 0.51 MB for the completed 256×176 views of these samples, around twelve times fewer image bytes than the original PNGs. The first tiny previews need less still. Extra requests and decoding also contribute to the measured time.

The original has sixteen times the pixels of that thumbnail, but compressed file sizes do not scale exactly with pixel count. The ten PNGs may finish close together because they are downloading concurrently under one shared limit.

What the counters mean

First frame records Emage's first decoded view. The PNG baseline records its load event; it does not measure any partial painting the browser may perform. These are different milestones, so the page labels them separately.

Finished is the time until the requested view completes. A target-sized view finishes when it reaches its chosen level; a full-size view continues through the original resolution.

Image bytes counts the downloaded image bodies, excluding metadata and network overhead. Gallery byte counters include completed downloads. Clicking an earlier downloaded level in the level viewer adds no network traffic.

What the comparison shows

The ten samples are distinct generated artworks, not a photographic benchmark. The full PNG and J2K versions preserve the same original pixels. In this set, the full J2K files are larger; the thumbnail advantage comes from downloading less resolution information.

The PNG baseline loads originals. A production gallery could instead use responsive image sizes, modern codecs, and caching. These experiments show the effect of progressive resolution selection, rather than establishing a universal winner between image formats.

The samples and loading behavior are checked automatically. Use the local checks to verify the setup, then run the demos for measurements in your browser.
