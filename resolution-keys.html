Resolution keys and authenticated grants

A recipient gets the key for a resolution, then derives the keys for coarser views. The storage server does not decide which details that key can decrypt.

A grant points toward coarser views

The finest key is the master. Each coarser key is derived from the next finer one, in one direction:

Ki−1 = SHA3-256(Ki)

K6 → K5 → K4 → K3 → K2 → K1 → K0

A recipient holding K3 can derive K2, K1, and K0. Those keys decrypt all information needed to reconstruct L3. The hash chain does not provide a way to derive K4, K5, or K6 from K3.

Try a coarse key and then the master in the owner/reader example. Both readers refer to the same stored ciphertext. A smaller requested display can reduce the chosen endpoint further; it cannot raise the key's ceiling.

Protect the detail separately

Emage encrypts the image's resolution levels under separate keys. A preview key unlocks the information needed for that preview and all coarser views. Finer detail remains encrypted.

The reader needs a granted key and the image's location. The browser handles the remaining encryption information automatically. Downloading the full encrypted file does not give a preview-key holder the missing keys.

The browser checks what the key grants

The browser first looks up which resolution belongs to the supplied key, without sending the key to the server. It then checks the key against the encrypted image itself before displaying the permitted view.

An unrelated key is rejected. A coarse key stays coarse even when the reader asks for a larger image. The server's delivery choice does not grant extra access.

Check the information being displayed

Encryption keeps image detail private; integrity checks detect changes to the information a reader is about to decode. Emage verifies the accessible levels before reconstructing their view.

A coarse grant checks its own accessible information. It cannot check finer encrypted detail whose keys it does not hold. A failed check produces an error rather than silently displaying a damaged image.

The project uses a custom integrity construction. These examples explain its behavior; they are not a cryptographic audit.

What the grant does not hide or revoke

Dimensions, headers, resolution structure, lookup metadata, and traffic patterns remain visible. A reader can copy a key they receive and can save pixels they are entitled to decode. A recipient can also enlarge a coarse raster locally; possession of fewer keys limits recovered image information, not the dimensions of an output canvas.

The API's shared upload password controls writes and deletes. It is separate from image decryption keys and is not a per-user read permission system. Key distribution is the application's responsibility. Deleting or replacing a server file cannot revoke ciphertext and keys someone has already saved.

For private material, keep originals and master keys out of public web assets and distribute grants through an appropriate channel. The article deliberately publishes its sample keys and PNGs, so its two panes demonstrate the mechanism using public artwork.
