How Emage works#

Emage delivers images in usable stages. Instead of waiting for an entire file to arrive, the browser decodes and renders a compact, genuine preview first, then sharpens the image as further detail streams in. When the page only needs a thumbnail, it can stop fetching as soon as that smaller target is met.

A single stored file backs every resolution. The browser handles all encoding and decoding locally through WebAssembly, leaving the server to store ciphertext and serve whichever byte ranges the client asks for.

Access control follows the same multi-resolution structure. A preview key only unlocks the data required for a coarse view, whereas the master key unlocks the full original. Because keys stay with the sender and the reader—never reaching the storage server—the server cannot read the image or decide how much detail a user is allowed to see.

Throughout this site, a layer refers to a spatial resolution level rather than a JPEG 2000 quality layer. Numbering starts at L0 for the coarsest preview, with each subsequent level adding finer spatial detail to the levels already in memory.

Choose a speed. Demo uses 2 MiB/s, between Everyday at 512 KiB/s and Fast at 4 MiB/s. Constrained uses 96 KiB/s. The proxy limits actual downloads; the images are not revealed by a timed animation. The three strategies run one after another. See how the experiments are measured.

A requests the coarsest zone, paints it, then appends the next zone until it reaches the target. B requests the same target packet window in one go and decodes once. C requests every level the master key allows. A and B should transfer the same image-body bytes for the same target; A spends more requests to get an earlier frame. C may spend much more bandwidth because it fetches detail the small display does not need.

That makes “faster” a question about what matters: the first useful preview, the final frame, total transferred bytes, or CPU work. A high-latency connection can make the extra progressive requests expensive. A fast connection can make the difference small. The demo reports those tradeoffs instead of assigning a universal winner.

Resolution-based access control#

An unrelated key is rejected. A valid key reveals only the resolution it grants and the coarser views below it.

Each key derives the keys for the coarser views below it:

Ki−1 = SHA3-256(Ki)

Holding K3 therefore gives access to K2, K1, and K0. It does not reveal K4. The reader checks the key's grant before displaying the image.

Choosing a smaller display can reduce the downloaded detail further. Choosing a larger display cannot exceed the key's grant.

Protocol overview#

The sender prepares one image with a pyramid of resolutions. The server can send just the parts needed for a requested level. The reader combines them into a view and checks that its key permits that much detail.

  1. Sender: prepare and encrypt the image at several resolutions.
  2. Storage server: keep the encrypted image and deliver the requested detail.
  3. Recipient: check the key and display its permitted view.

Small first, detail next#

A progressive load starts with the coarsest view. Each later request adds new detail to bytes already downloaded. It does not start the image over or repeatedly download the earlier levels.

The browser authenticates and decrypts the permitted information before rendering. The server handles storage and delivery without receiving image keys. Dimensions and resolution information remain visible.

Other applications#

The pattern is useful wherever “enough detail” depends on the device, the connection, or the person holding the key. These are possible applications, rather than products this repository already implements:

  • Private previews and archives. Browse small permitted previews while retaining a separately distributed grant for the original. One stored codestream can serve both.
  • Field inspection and intermittent links. Get a coarse view of a captured scene first, then spend bandwidth on more resolution when the link and the task justify it.
  • Publishing and review workflows. Share a proof-resolution grant, then distribute a finer key when the workflow calls for it. The image payload can stay in the same storage location.
  • Large visual collections. Fetch bounded thumbnail windows for a contact sheet and request finer levels when an item becomes the focus. The present implementation grants whole-image resolution, not spatial tiles or arbitrary regions.

Resolution control is not redaction: a coarse image still reveals information. A distributed key cannot be taken back by changing a button or revoking an HTTP session. Revocation needs new encryption and new key distribution. Identity, key delivery, storage policy, and transport security remain application responsibilities.

Emage's contribution is the connection between an image's resolution structure, the bytes needed to reconstruct it, and the keys allowed to unlock those bytes. The experiments above make each part visible: what arrived, what rendered, and what the supplied key actually permitted.
